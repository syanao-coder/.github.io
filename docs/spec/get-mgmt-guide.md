## 3. 🔴 スキルはそのまま読み込める形式で出す（出力形式と設置の確認）

**スキルを更新したら、ユーザーが編集せずにそのまま設置できる状態で出力する。**
差分・抜粋・「この節を置き換えてください」形式で出さない。

| 項目 | 規約 |
| :--- | :--- |
| 単位 | **1スキル＝1ファイル全文。** 変更が1行でも全文を出す |
| ファイル名 | **`SKILL.md`。** スキル名のフォルダに入れて出す（例: `get-dev-workflow/SKILL.md`） |
| 先頭 | **YAML フロントマター（`---` / `name:` / `description:` / `---`）を必ず含める。** これが無いとスキルとして読み込めない |
| 出し方 | ファイルとして出力する。**チャット本文へ貼るだけで終わらせない** |
| 複数スキル | 同時に出すときも1ファイルずつ。**1ファイルにまとめない** |

⚠️ **`description` も更新対象である。** その版で追加した機能の語句を入れておかないと、
必要な場面でスキルが呼び出されなくなる。

⚠️ **ファイル名が3つとも `SKILL.md` になる。** どれをどのフォルダへ入れるかを
出力時に必ず明記すること。

🔴 **レビュー用に受け渡すときは名前を変える。**
設置時のファイル名は `SKILL.md` でなければならないが、**同名のまま複数を同時に
アップロードすると上書きされて1つしか残らない**（2026-07-29 に実際に発生。3ファイル渡して
1ファイルしか届かず、1往復を無駄にした）。

| 方向 | ファイル名 |
| :--- | :--- |
| 出力（設置用） | `<スキル名>/SKILL.md` |
| 受け渡し（レビュー用に戻すとき） | `chat_SKILL.md` のように**区別できる名前**にする。1つずつ渡すのでも良い |

**受け取った側は、届いたファイル数と期待した数が合っているかを最初に確認すること。**

🔴 **パッチスクリプトは `assert old in src` と `assert src.count(old) == 1` の2重ガードで書くこと。**

2026-08-03、開発用セッションの作業ディレクトリの `controller.html` が
**書いた覚えのない内容に変わっていた**（版数の行番号がずれ、ラベルが書いていない文字列になっていた）。
**気づけたのは `assert old in src` が一致せずに落ちたから**である。
2026-07-31 の「45行消失」と同じ構造の事故で、**このガードは検出器として機能する。**
復旧は**利用者へ渡した最終版を基点に取り直す**こと（作業用コピーは捨てる）。

🔴 **設置されたことの確認は、管理用セッションが①へ入る前に行う**（2026-08-02 追加 / 利用者提案）。

出力して終わりにしない。**スキルを実際に読むのは次の開発用セッションであり、
古いスキルのまま指示書を渡すと、開発用セッションが古い仕様を正として実装する。**
④と①の境目が最後の防波堤である。

| 手順 | 内容 |
| :--- | :--- |
| 1 | 利用者へ「7本とも設置したか」を聞く |
| 2 | **各スキルの説明文（`description`）に、そのVerで足した語句が入っているかを7本とも見る** |
| 3 | 1本でも古ければ、**指示書を渡さずに**どれが古いかを名指しで報告する |

🔴 **確認できるのは説明文だけである。ファイル本文では確認できない。**

#### 🔴 指示書に行番号を書かない ★2026-09-06

**`/mnt/skills/user/` から読めるのはセッション開始時のスナップショットである。**
そのため **④でスキルを更新した直後に指示書を書くと、行番号が必ずずれる。**

⚠️ **2026-09-06、管理用セッションが分割専用セッションへ渡した参照の一覧は、
行番号が実物と 30〜90行ずれていた**（例: `get-protocol-spec` の 3-7節参照を「1098行」と
書いたが実際は 1189行）。**参照の実体はすべて存在したので実害は出なかったが、
受け取った側が文字列照合へ切り替えて回避しただけである。**

| 書き方 | 可否 |
| :--- | :--- |
| **参照している文字列そのもの**を引用する | ⚪ **これを使う** |
| 行番号 | ❌ **書かない。** 書くなら「参考値・照合は文字列で行うこと」と明記する |

🔴 **同じ理由で、自分が④で更新したスキルの本文は、そのセッション中は古いまま見える。**
**更新した内容を前提に別の作業をするときは、利用者に現物を出してもらうこと。**

| 見るもの | 設置後に更新されるか |
| :--- | :--- |
| **スキルの説明文** | ⚪ **される。** これが唯一の確認手段 |
| `/mnt/skills/user/<スキル名>/SKILL.md` の中身・行数 | ❌ **されない。** セッション開始時の内容で固定されており、設置しても**そのセッションが終わるまで旧版のまま読める** |
| ナレッジのコード（`/mnt/project/`） | △ 更新されるが**遅れる。** 古く見えたら1ターン置いて取り直す（2026-08-02、反映済みの v2.7.1 を未反映と誤認して1往復無駄にした） |

2026-08-02、この手順を「ファイルを読み直して行数を突き合わせる」と書いて**空振りした。**
3本とも旧版の行数（393 / 944 / 952）で読め、説明文だけが新しかった。

🔴 **`description` には 1024文字の上限がある。超えると設置できない**（2026-08-05 に `get-protocol-spec` が
1,066文字になり設置エラー）。**版ごとに追記していくと必ず溢れる。**

| 説明文に書くもの | 書かないもの |
| :--- | :--- |
| 呼び出しの引き金になる語句（扱う主題・節の名前・固有のメッセージ名） | **版ごとの変更点の羅列。** 正本は各スキルの版数履歴（`/get-protocol-spec` 0-3節） |
| そのVerで足した語句（設置確認用・下記） | 本文を読めば分かる詳細 |

**溢れたら、まず版数の羅列を削る。** 現行版と主な経緯だけ残せばよい。

🔴 **`description` に山括弧の対（`<span>` `<div>` `<script>` など）を書いてはいけない。**
バッククォートで囲んでも**コードとして扱われず**、設置時に
**`description cannot contain XML tags`** で弾かれる（2026-08-07 / `get-ui-spec` の新設時に発生）。
**本文には書いてよい。制約があるのは説明文だけである。**
書きたいときは `span 要素` のように**タグの形にしない**で書く。
⚠️ 1024文字の上限と同じく、**出力時に機械的に検査すること**（`[<>]` を含まないこと）。
目安の文字数（2026-08-05 時点）: `get-protocol-spec` 862 / `get-dev-workflow` 約800 / `get-chat-feature-spec` 689。

🔴 **そのVerで足した語句を、必ず `description` にも入れておくこと。**
**本文にしか書かなかった変更は、確認する手段が存在しない。**
同日、`get-dev-workflow` を2回出力（428行 → 444行）したが、差分が本文だけだったため
**どちらが設置されたか機械的に判別できず、利用者に本文を検索してもらう羽目になった。**

🔴 **設置は1本ずつ行い、そのつど反映を確認する**（2026-08-01 追加）。

3本まとめて設置すると、一部だけ反映されないことがある（実測: 2026-07-27〜07-31 にかけて
`get-chat-feature-spec` と `get-protocol-spec` が**5日間まったく反映されず**、
`get-dev-workflow` だけが通っていた）。反映の確認は
**スキルの説明文にそのVerの語句が入っているか**で行う。

🔴 **編集する前に、手元の版と最新版の行数を突き合わせること。**
古い版を基点に編集すると、その間に入った変更が消える
（実測: 2026-07-31 に `get-dev-workflow` の1節ぶん・45行が消失した）。

## 4. スキルを増やす／分ける判断 ★2026-10-04 改訂（分割の規約を削除）

🔴 **行数を理由にした分割はしない**（2026-10-04 利用者と合意）。旧規約（目安 1,200行・分割専用セッション・分割の手順）は削除した。

| 理由 | 内容 |
| :--- | :--- |
| 前提が消えた | 目安と手順は claude.ai の制約（説明文の常時読み込み・設置事故が本数に比例・開発用と管理用のセッション分離）から作られた。Claude Code では仕様書はただのファイルで、セッションも1つ |
| 効果が小さい | 必要な節は grep や節ごとの読み出しで引ける。過去の分割でも「効いたのは必ず読まれる1本だけ・効果は僅か」と評価していた |
| 事故の種になる | 分割のたびに節番号の参照が宙に浮いた（2026-08-07 7件・08-15 2件・09-06 12件） |

- 大きいことで困るのは「探しにくさ」だけ。**節の見出しを保ち、終わった経緯は history へ退避する（5節）**ことで対処する。
- それでも節を別ファイルへ移すときは、🔴 **移す本文が指す節番号・スキル名を機械で列挙して1件ずつ確かめ、元の場所に1行の参照を残す**（上の事故の教訓）。
- 過去の分割の記録（`get-ui-spec` / `get-debug-suite` / `get-danmaku-spec` / `get-mgmt-guide` の分離）は各スキルの冒頭と git の履歴にある。

## 5. history への退避規約

**管理用セッションのみが行う。**

| ファイル | 対象 |
| :--- | :--- |
| `history_chat.md` | `/get-chat-feature-spec` から剪定した内容 |
| `history_protocol.md` | `/get-protocol-spec` から剪定した内容 |

### 退避するもの

- 実測データの詳細表（結論だけスキルに残す）
- 撤去した機能の実装記録
- 失効した罠・環境依存の記述
- 事前想定が覆った記録
- 検証に使った動画IDとその特性
- スキルから消したが、なぜそうなったかを追うのに要る経緯

### 退避しないもの（スキルに残す）

- 現行構成で有効な制約・罠
- 恒久的な行き止まり
- 確定した定数とその判定基準
- データ構造・メッセージ一覧

**スキル側には「詳細は history を参照」と一言だけ残す。**

## 6. セッションの作り直しと引き継ぎ（コンテキスト肥大化対策）

**管理用セッションも、開発用セッションと同じように時折作り直す。**
長く使うほど文脈が膨らみ、過去の指示を取りこぼし始める。

### 6-1. 切り替えてよい場所

**判断基準は「このセッションにしか無い情報が残っていないか」の一点。**

| 場所 | 可否 | 理由 |
| :--- | :--: | :--- |
| **④（スキル更新・剪定・history 退避）の直後** | ✅ | 決まったことがすべてスキルと history に出ている |
| **①（指示書の作成）の直後** | ✅ | 指示書が完成していれば、②は開発用セッションの仕事で管理用は待つだけ |
| ①の途中（検討中・指示書が未完成） | ❌ | 却下した案や検討の経緯が文書化されていない |
| ③〜④の途中（報告書を受け取ったが剪定が未了） | ❌ | 剪定の判断が中途半端に残る |

🔴 **①の直後に切り替える場合は、1節のサイクル位置を「②進行中」にし、
渡した指示書のファイル名を書いてから切ること。**
ここが `次は①` のままだと、**新しいセッションが指示書を書き直す**
（2026-08-02 に実際に起きかけた）。

### 6-2. 頻度の目安

| タイミング | 判断 |
| :--- | :--- |
| 毎バージョン | 細かすぎる。スキル全体の読み直しが毎回かかる |
| **1〜3バージョンごと、④の直後** | 推奨 |
| 大きな設計転換のあと | 推奨（v2.6.0 の取得方式転換のような場面） |
| 応答が鈍い・過去の指示を取りこぼし始めた | 即座に |

### 6-3. ⭐ 引き継ぎは、スキルの検査として使う

**新しいセッションが「スキルに書いてあるべきこと」を質問してきたら、それはスキルの欠陥である。**
答えて終わりにせず、**その場でスキルへ追記すること。**

実例: 2026-07-27 に管理用セッションを立ち上げた際、
「v2.6.2 と v2.6.3 の実機検証は済んでいるか」を最初に確認する必要が生じた。
原因はスキルの現在地が**2世代古いまま**だったこと（コードは v2.6.3、スキルは v2.6.1）。
→ 1節「現在の状態」とサイクル位置の更新を規約化した（`/get-dev-workflow` 1節）。

### 6-4. 新しいセッションの立ち上げ方

最初に `/get-dev-workflow`・`/get-protocol-spec`・`/get-chat-feature-spec` を読む。
そのうえで **1節のサイクル位置**を見て、自分が①から始めるのか④から始めるのかを判断する。

⚠️ **スキルとナレッジのコードの版数が食い違っていたら、まず食い違いを報告すること。**
古い方に合わせて作業を進めない。

### 6-5. なぜ開発用セッションがスキルを触らなくなったか（2026-08-01 の変更）

v2.7.0 まで、開発用セッションが③でスキルを更新し、管理用セッションが④で剪定していた。
**この分担をやめ、④に統合した。** 理由は3つで、いずれも実際に起きた事故である。

| 理由 | 実例 |
| :--- | :--- |
| **二度手間** | 開発用セッションが書いた `⚪ v2.6.5 で解消` を管理用セッションが `⚠️ 落ちる仕組みは残る` へ書き直した。理由コードの表は3箇所に重複して書かれ、1箇所ずつに割り当て直した |
| **版の取り違えで内容が消える** | 2026-07-31、開発用セッションが1つ前の版を基点に編集し、`get-dev-workflow` の1節ぶん（45行）が消失した |
| **往復コスト** | 同じ内容のスキル3本（約2,200行）を、開発用セッションが出す → 設置 → 管理用セッションが受け取る → 剪定して再度出す → 再設置、と2周させていた |

**代わりに報告書の必須項目を規約化した**（`/get-dev-workflow` 3-1節）。
報告書に書かれなかったことは反映されないので、開発用セッションは `/get-dev-workflow` 3-1節を必ず満たすこと。

⚪ **新方式の初回は v2.7.1**（2026-08-02）。**必須項目10点はすべて満たされ、規約側の修正は不要だった。**
スキル3本の往復も1周で済んでいる。`/get-dev-workflow` 3-1節へ足したのは「測れなかった値」の1項目のみ。
