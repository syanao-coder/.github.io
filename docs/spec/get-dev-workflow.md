## 0. 体制 ★2026-10-04 改訂

**Claude Code の1セッションが、指示書・実装・記録・仕様書の更新を行う**（流れは `CLAUDE.md` 4-3節）。
旧来の「管理用セッション / 開発用セッション / 分割専用セッション」の分担と、ナレッジ・スキル設置を前提にした手順は廃止した（2026-10-04 利用者と合意）。本文中に残る「管理用セッション」「開発用セッション」は経緯の記録として読む。

残す原則:

| 原則 | 理由 |
| :--- | :--- |
| 🔴 **仕様書（`docs/spec/`）の更新は④（版を締めるとき）に集める** | 途中で書くと「状態の表が失効する」（鉄則 #36） |

## 1. 1バージョンの開発サイクル

段と主体は `CLAUDE.md` 4-3節が正本（① 指示書 → ② 実装・判定・用紙 → 利用者の測定 → ③ 記録 → ④ 利用者に確認して仕様書更新・版数確定）。

### 各ステップの完了条件

| ステップ | 完了とみなす条件 |
| :--- | :--- |
| ① | Ver番号・含む項目・除外した項目とその理由・着手前に確かめた実コードが指示書に書かれている |
| ② | **全テスト項目の合否がユーザーから返ってきている。** 未実施があれば未実施と明記されている |
| ③ | 記録（`docs/reports/`）が 3-1節の必須項目をすべて満たしている |
| ④ | 仕様書の「現行リリース」「最終検証日」が新Verになり、重複・失効した記述が消えている。`/get-mgmt-guide` 1節と `CLAUDE.md` 3節の現在地が新Verになっている |

⚠️ **②が終わる前に③をやらない。** 検証で覆る可能性がある内容を記録に確定として書くと、
撤回済みの設計が仕様として残る（過去に実際に発生している。
「アドオンだけでは原理的に不可能」という誤った結論が仕様書に残った例）。

### 1-4. 版数を切らないスパイク ★2026-08-04

**可否が未確定で、結果によって次の版数そのものが変わる作業は、版数を切らずに単独で走らせる。**

| 条件 | 扱い |
| :--- | :--- |
| 結果によって続きが**マイナーかメジャーかすら決まらない** | 🔴 **スパイクにする。版数を切らない** |
| 成果物 | **単独ファイル**（`spike_*.html` / `*_lab.html`）。本番からリンクしない＝表側から到達できない |
| 本番コード | **触らない。** `APP_VERSION` も `manifest.json` も動かさない |
| 撤退 | ファイルを削除して終わり |
| 記録 | 3-1節の必須項目は同じ。変更ファイルは**「本番コードへの変更なし」**と書く |

**先例**: `danmaku_lab.html`（v2.7.0 の計測）/ `spike_5a.html`（メンバー限定の埋め込み可否 / 2026-08-04）。

🔴 **測定に使ったブラウザの「実体」を報告書に必ず書かせること。**

| 場面 | 使うブラウザ |
| :--- | :--- |
| ローカルのウェブサーバーでのテスト | **Firefox**（`about:debugging` でアドオンを読み込むためデバッグ準備が容易 / 利用者の運用） |
| GitHub Pages でのテスト | **どちらでもよい。使った方を報告書へ書く**（2026-08-15 緩和） |
| ブラウザ差を疑う場面が出たとき | 🔴 **そのときに Firefox 本家で再測する** |

⚠️ **「Cookie 関連は必ず Firefox 本家で判定する」という旧規約は 2026-08-15 に緩和した。**
元は 5-A5 の「Floorp では再生できない」という**誤った結論**に由来しており、
5-A6 でブラウザ差が無いことが確定している。**v2.7.5 は全測定を Floorp で行い、取得も再生も成功した。**
| 可否が決まったあとの実用確認 | **Floorp でも行う**（本プロジェクトは Floorp を対応対象にしており、**利用者の常用環境**） |

⚠️ **Firefox 本家と Floorp の両方が測定環境として存在する。** 判別は `about:support` の
**「アプリケーション基本情報 → 名前」**でしか行えない。**報告書の冒頭に必ず書かせること。**

🔴 **ブラウザ差を疑う前に「ページ差」を疑うこと**（2026-08-06 / 5-A5 → 5-A6 の教訓）。

5-A5 は「同一の Firefox 153 系・同じ設定・同じ Cookie・拡張機能ゼロの新規プロファイルでも、
Firefox 本家では再生でき Floorp では再生できなかった」として **「Floorp 本体側の問題」と結論した。**
**その結論は同日に覆った。** 同じ Floorp・同じ保護設定・同じオリジンでも、
**本番コントローラーでは再生できた。差はブラウザではなく測定に使ったページ側にあった。**

⚠️ **スパイク用のページは本番と作りが違う。** `spike_5a.html` は3つのプレイヤーを同時に埋め込む。
**「同じ条件」と言うとき、ページの作りが条件に入っているかを確かめること。**
🔴 **可否を結論づける前に、一度は本番のページでも同じことを試すこと。**

**実測環境（2026-08-06 時点）**

| 項目 | 値 |
| :--- | :--- |
| OS | **Windows 11**（⚠️ それ以前の報告書の「Windows 10」は誤り。**同じ環境である可能性が高い**） |
| Firefox 本家 | **153.0.3** / ビルド **20260803132010** |
| Floorp | **12.16.4@153.0** / ビルド **20260725075208** |
| 利用者の Floorp | `Rasenwatch`（別の同時視聴用拡張）が入っている。⚠️ **将来 YouTube ページ上で本プロジェクトのアドオンと競合しうる** |

🔴 **Floorp は UA に `Firefox/153.0` を名乗るため、測定データからは判別できない。**
2026-08-05、スパイク 5-A2 の設定画面のスクリーンショットで**初めて Floorp と判明**し、
**5-A・5-A2 の全測定が Floorp 上だった可能性**が残った。**人が書かない限り記録に残らない。**

---

🔴 **前回と同じ測定を繰り返す作業は、同じセッションで続けること。**
版ごとにセッションを分ける原則（0節）は、**計測器を共有する再測には当てはまらない。**
計測器を作り直すと、**値が変わったときに「条件の差」なのか「計測器の差」なのかを区別できなくなる。**
セッションを作り直す場合は、引き継ぎ文書に **「計測器を作り直さず、現物をそのまま使うこと」**を明記する。

根拠: 5-A2 の A2-3（拡張機能を無効化して再測）・A2-4（同一ディレクトリで再測）は
**5-A とまったく同じ測定の繰り返し**であり、目的は「150 が再現するか」の一点。
`spike_5a.html` が別物になると、切り分けのための再測が**別の切り分け不能を生む**（2026-08-04）。

⚠️ **測る対象も計測器も違う作業は、従来どおり分ける。**
例: 5-C（チャット取得側）は `spike_5a.html` を使わないので、5-A2 を閉じたあと別セッションで始める。

🔴 **スパイクの報告では、観測した事実と解釈を分けて書かせること。**
`/get-chat-feature-spec` には **iframe 方式の検証で「これが決定的」と3回宣言し3回とも外した**記録がある。
事実の欄にはエラーコード・表示された文言・時刻だけを置き、解釈は別欄に「〜の可能性がある」と書く。
**「判定保留」は失敗ではない。分からなかったことを分からなかったと報告するのが正しい。**

| :--- |

### 2-0. 🔴 指示書に「読む仕様書」を書く ★2026-09-06 / 2026-10-04 改訂

指示書の冒頭に、その版で読む仕様書を書く（後で読み返す自分のため）。

| # | 規約 |
| :-: | :--- |

### 2-1. 構成

🔴 **手順書と回答用紙は1つのファイルにする**（2026-08-30 / 利用者提案・別プロジェクトからの移入）。
手順のすぐ下に回答欄を置く。**別ファイルにしていた `answer_form.html` は廃止**（3-1-2節）。
⚪ **番号のずれ（鉄則 #30 で作り直す原因になった）が構造的に起きなくなる。**

| 要素 | 書き方 |
| :--- | :--- |
| 前置き | **短く簡潔に。** 何のテストか1〜2行 |
| 前提条件 | **詳細に。** 環境・準備手順・事前に戻しておく設定 |
| 変数・動画ID | **手順書内に表で列挙する。** 値が確定していないものは「要記入」と明示 |
| テスト項目 | 1項目ずつ独立させ、手順と合格条件を対にする |
| 手順 | **どのアプリをどう開き、何を貼り付け、何が出れば成功か**まで書く |
| 合格条件 | **表で示す。** 「正常に動くこと」のような主観的な書き方をしない |
| 後始末 | 変更した設定を戻す手順を項目ごとに書く |

### 2-2. 🔴 作成の鉄則

v2.6.4 の検証で、手順書の不備により**4回の手戻り**が発生した。原因はすべて
「その項目だけを見ても実施できない書き方」にあった。以下は再発防止の規約である。

⚪ **v2.6.5 の検証は手戻り0回**（全11項目・1ラウンド完了）。#1〜#9 が効いた。
#10・#11 は v2.6.5 で新たに必要と分かったもの。

⚠️ **v2.7.0 の検証は手戻り3回**（ラボ2回・本体1回）。#12〜#14 はそこから追加した。
うち1回は **#11 を人手の確認で済ませたために抜けた**もので、
「毎回」「機械で」やることを #11 自体へ書き込んだ。

⚠️ **v2.7.1 の検証は手戻り2回**（全13項目）。**どちらも手順書側の問題でコード修正は発生していない。**
#15・#16 はそこから追加した。#11 の機械化は効き続けている（下の「⚪ 効いている鉄則」）。

🔴 **#12〜#14 は「自作の検証ツール（ラボ）を使う場合」の鉄則である。**
本番のUIそのものが検証対象のときは適用できない。

| 場面 | #12〜#14 の扱い |
| :--- | :--- |
| **常設の自動デバッグ基盤で測る（v2.7.3 以降の `debug_suite.js` / 8節）** | 🔴 **これを第一候補にする。** #12（1手順1ボタン）は**テストごとの実行ボタン**として実現済み。#13 は成立しない（基盤は本番UIの中にある）ので、**`clickReal()` の被覆判定と positive control で代替する**。#14（素材の密度）は変わらず適用 |

⚪ **機械化が目視を代替できた実例**: 設定メニューが動画に重なるため「コメントが消えたか」を
目視判定できなかったが、**100ms間隔でサンプリングし「画面上0件になった回数」を数える**形にして
判定できた（v2.7.1: 79回・最小18件 / v2.7.2: 80回・最小2件。**いずれも0回**）。
**#13 を守れない場面でも #4 で回収できる。**

⚠️ **#13 を守れない版が2回続いている。** UI自体が検証対象の版では、
**「重なっているかどうか」そのものを測る項目を立てる**とよい
（v2.7.2 の R2: パネルと動画領域の重なり面積 43.5% を実測して合格とした）。

| # | 鉄則 | 破ったときに起きること |
| :-: | :--- | :--- |
| 1 | **各項目に前提・変数の実値・操作場所を重複して書く。** 項目間に前後依存を作らない | ある項目の後始末が次の項目の前提になり、追う対象が分散する。🔴 **2026-08-31 に3回目の再発。** `D-C5` が `D-C2` の `chatStore` 残骸を読む作りだったため、**本体 v2.8.3 が仕様どおり捨てた瞬間に恒常的に判定不能**になった。⚠️ **「いま通っている」は根拠にならない。本体が正しく直ると壊れる依存がある。** 手元に無ければ自分で用意する自己完結型にすること |

| 8 | **判定の閾値を実測の幅より狭く置かない。** 先に幅を測ってから閾値を決める | 正常なばらつきを不合格と誤判定する |
| 9 | **計測の起点をジョブ開始以外に置かない** | 人間の操作時間が所要時間に混入する |
| 10 | **同じ表示に至る経路が複数あるなら、経路ごとに項目を分ける。** 「どちらでも同じ結果」を前提にしない | 片方の経路だけ直っていることに気づけない。v2.6.5 では取得直後（`refreshChatCardsFor`）と開き直し（`updateChatContent`）で通るコードが違い、分けなければ片方が未検証で残った |
