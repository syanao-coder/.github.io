## 0. バージョン管理規約

### 0-1. 版数はA側とB側で共通

**1つのリリース = 1つの版数**。A側だけ／B側だけを更新した状態で動かさない。

| 側 | ファイル | 版数の定義箇所 |
| :--- | :--- | :--- |
| A | `controller.html` | `const APP_VERSION = 'x.y.z';`（`<script>` 冒頭） |
| B | `manifest.json` | `"version": "x.y.z"` |

**A側のみ／B側のみを変更した場合も、両方の版数を上げて揃える。**
「HTMLは変えていないから据え置き」をやると照合が機能しなくなる。

### 0-2. 採番ルール

- `x.y.Z`（パッチ）… 不具合修正、既存機能の調整。**プロトコル無変更ならここ**
- `x.Y.0`（マイナー）… 機能追加、プロトコルへのメッセージ追加
- `X.0.0`（メジャー）… 既存プロトコルの破壊的変更

**欠番**: 動作不良で撤回した版数は再利用せず欠番にする。
- ❌ **v2.4.1 は欠番**（➕送信ボタンが表示されなくなり撤回）

🔴 **配布の都合でパッチを切ることがある ★2026-09-05 追加**

**同じ版数のアドオンは上書きインストールできない。**
測定中に不具合が見つかって修正版を出すとき、**その版数が既に相手の手元に入っていると、
同じ版数のままでは配れない。** このときはコードの変更の大小にかかわらず**パッチを1つ上げる。**

⚠️ **`2.8.3.1` のような4桁は規約に無い。採らないこと。**
⚠️ **`index.html` の中身が変わらなくても版数は上げる。** バッジが HTML とアドオンの版数を
突き合わせるため、据え置くと橙（不一致）になる（0-4節）。
🔴 **修正版を出す前に「その版数が既に相手の手元に入っているか」を確認すること。**
先に聞いていれば切り直さずに済んだ（2026-09-05 / v2.8.3 → v2.8.4）。

### 0-4. 整合チェックの仕組み

```
content_controller.js  起動時
  └─ chrome.runtime.getManifest().version を取得
       └─ window.postMessage({ type:'EXTERNAL_SYNC_EVENT', state:'addonInfo', version })
            └─ controller.html が APP_VERSION と照合し、トップバーのバッジへ反映
```

A側のリスナー登録が間に合わない場合に備え、**0ms / 300ms / 1500ms の3回**送信する。

| バッジ表示 | 色 | 意味 |
| :--- | :--- | :--- |
| `v2.8.1` | 緑 | 一致。正常 |
| `HTML v2.8.1 ⇔ アドオン v2.6.1` | 橙 | **不一致。古い方を差し替えること** |
| `v2.8.1 / YouTube権限なし` | 橙 | 版数は一致しているが youtube.com の実行許可が無い ★v2.7.0（4-1節） |
| `v2.8.1 / アドオン未検出` | 赤 | アドオンが応答していない（8節の最重要項目） |

判定タイムアウトは 4000ms（`ADDON_DETECT_TIMEOUT_MS`）。

⚠️ v2.6.0 以降は youtube.com の `host_permissions` が常時必要。
**「YouTube権限なし」は v2.7.0 で橙バッジとして区別できるようになった**（4-1節）。
v2.6.4 で見送った経緯は `history_protocol.md`。

### 0-6. 取得エンジンの版数照合 ★v2.6.4

版数バッジ（0-4節）が見るのは **`manifest.json` の版数**であって、
**取得タブの MAIN world で実際に動いているエンジンの版数ではない。**
隠して保持した取得タブでは旧エンジンが生き残るため（8節🔴）、両者はずれうる。

```
background.js  ensureInjected(tabId)
  ├─ executeScript(ISOLATED, content_yt_chat.js)
  ├─ executeScript(MAIN, func) … window.__SYNC_CHAT_EXPECTED_VERSION = manifest の版数
  │                               ★毎回上書きされる
  └─ executeScript(MAIN, chat_fetcher_main.js)
       └─ 構築時に1回だけ読む → const ENGINE_VERSION（以後変わらない）
```

| 診断口（取得タブの MAIN world） | 返すもの |
| :--- | :--- |
| `__syncChatEngine.version` | エンジンが**構築時に**受け取った版数。固定 |
| `__syncChatEngine.expected()` | 注入側が**最後に**置いた版数 |
| `__syncChatEngine.stale()` | 両者が食い違えば `true`＝旧エンジンの生き残り |

🔴 **`background.js` の `ready` 照合警告は、旧エンジン生存時には発火しない。**
`chat_fetcher_main.js` は冒頭の `if (window.__syncChatEngine) return;` で早期脱出するため、
旧エンジンが残っているタブへ再注入しても **`ready` そのものが post されない。**
この警告が意味を持つのは `__SYNC_CHAT_EXPECTED_VERSION` が未設定で `(unknown)` になった場合
（＝注入手順が崩れた場合）の安全弁としてのみ。
**旧エンジン生存の実際の検出役は `stale()` である。**

⚠️ `ready` は `content_yt_chat.js` が中継し、**`background.js` で消費して終わる。**
A 側へは流さないため、この機構でプロトコルは変わっていない。

## 2. 全体の経路

### A → B（コントローラーから配信サイトへの命令）

```
controller.html
  └─ window.postMessage({ type:'SYNC_CMD', action, value })
       └─ content_controller.js (file://・localhost・GitHub Pages)
            └─ chrome.runtime.sendMessage({ type:'SYNC_COMMAND', action, value })
                 └─ background.js
                      └─ chrome.tabs.sendMessage(tabId, { action, value })
                           └─ content_video.js ── (video要素を操作)
```

### A → B（コントローラーからYouTubeタブへの結果通知）★v2.3.0

```
controller.html
  └─ window.postMessage({ type:'CONTROLLER_TO_YOUTUBE', event:'addVideoResult', ... })
       └─ content_controller.js
            └─ chrome.runtime.sendMessage({ type:'YOUTUBE_ADD_RESULT', ... })
                 └─ background.js  ── chrome.tabs.query({ url:['https://*.youtube.com/*'] })
                      └─ chrome.tabs.sendMessage(tabId, { type:'YOUTUBE_ADD_RESULT', ... })
                           └─ content_youtube_scrape.js ── (➕送信ボタンの表示を更新)
```

### InnerTube 直接取得（★v2.6.0 / v2.6.2 以降は唯一の経路）

```
controller.html
  └─ window.postMessage({ type:'CHAT_STREAM_REQUEST', videoId, requestId })
       └─ content_controller.js
            └─ runtime.sendMessage({ type:'FETCH_CHAT_STREAM', videoId, requestId })
                 └─ background.js
                      ├─ youtube.com タブを確保（軽量な https://www.youtube.com/ 1枚を共用）
                      ├─ scripting.executeScript({ world:'ISOLATED' })  … 中継スクリプトを注入
                      └─ scripting.executeScript({ world:'MAIN' })      … 取得ループを注入
                           │
                           ▼ 取得ループ（MAIN world / ページオリジン）
                           └─ window.postMessage({ __syncChat:1, ev:'chunk', ... })
                                └─ content_yt_chat.js（ISOLATED）
                                     └─ runtime.sendMessage({ type:'CHAT_CHUNK', ... })
                                          └─ background.js（中継のみ）
                                               └─ tabs.sendMessage(controllerTabId, {...})
                                                    └─ content_controller.js
                                                         └─ window.postMessage(... state:'chatChunk')
                                                              └─ controller.html
```

⚠️ **MAIN world には `browser.*` API が無い。** 結果を返す手段は `window.postMessage` のみで、
ISOLATED の content script が受けて中継する構造が**必須**である。

⚠️ **content script（ISOLATED）から fetch してはいけない。** Firefox では拡張機能の principal で
飛ぶため `Origin: moz-extension://` となり HTTP 403 になる。取得は必ず MAIN world で行う。

### B → A（配信サイト・YouTube・チャットの報告）

```
content_video.js / content_youtube_scrape.js / background.js
  └─ chrome.runtime.sendMessage({ type:'VIDEO_STATE_CHANGE' | 'YOUTUBE_ADD_VIDEO', ... })
       └─ background.js
            └─ chrome.tabs.sendMessage(tabId, { type:'EXTERNAL_STATE_UPDATE' | ... })
                 └─ content_controller.js
                      └─ window.postMessage({ type:'EXTERNAL_SYNC_EVENT', state, ... })
                           └─ controller.html ── (addEventListener)
```

| seekTo | 絶対秒（数値） | 絶対時間シーク | ✅ | ✅ |
| speed | 倍率（数値） | 再生速度変更 | ✅ | ✅ |
| requestTime | なし | 現在時間の報告要求 | ✅ | ✅ |

実装上の注意:
- seek / seekTo は `content_video.js` 側でイベントを手動発火させていない（`currentTime` 代入のみ）
- seekTo のみシーク後 50ms で再生/停止状態を補正する処理あり
- **v2.4.3 の再生同期でメッセージは追加していない。** A側が pause → seek → play を
  既存コマンドのまま時間差で送るだけで成立する（§9）
- pause と seek は到着順が入れ替わっても最終状態が同じ（可換）なため、
  `background.js` が毎回 `chrome.tabs.query` を挟むことによる順序非保証は実害にならない

### 4-1. YouTube 実行許可の問い合わせ ★v2.7.0

Firefox の MV3 は `host_permissions` がオプトインで、アドオンの再読み込みや更新の後に
YouTube の許可が外れることがある（8節🔴 の最重要項目）。外れたままだとチャット取得だけが
失敗し、バッジは緑のままなので**画面から理由が読めない。** これを表示するための往復。

| # | 経路 | メッセージ |
| :-: | :--- | :--- |
| 1 | `content_controller.js` → `background.js` | `{ type:'QUERY_YT_PERMISSION' }` |
| 2 | `background.js` → `content_controller.js` | `{ type:'EXTERNAL_YT_PERMISSION', granted:<bool> }` |
| 3 | `content_controller.js` → ページ | `{ type:'EXTERNAL_SYNC_EVENT', state:'ytPermission', granted:<bool> }` |

- 問い合わせは `content_controller.js` が**自分の判断で**投げる。**A側からの問い合わせ経路は作らない**
  （A→B のメッセージを増やさずに済み、既存の `SYNC_CMD` と混ざらない）
- `addonInfo` と同じ **0ms / 300ms / 1500ms の3連投**に乗せる。A側のリスナー登録が
  間に合わない問題は権限側にも等しく起きるため
- `window` の `focus` でも投げ直す。**別タブで許可を与えて戻ると再読み込みなしで緑へ戻る**（実機確認済み）
- 🔴 **`sendResponse` を使わない。** `background.js` のリスナーは全分岐が同期応答で
  統一されている（`return true` を一切使っていない）。ここだけ非同期応答を持ち込むと
  リスナー全体の戻り値の扱いを変えることになる。**`sender.tab.id` へ押し返す**
- 判定は既存の `hasYouTubePermission()`（`ytOriginPatterns()` を manifest から引く）を再利用する。
  **パターンを手で書き写さない**

🔴 **この判定で処理を止めてはいけない。** バッジは表示専用である。
`ytPermission === false` を理由にチャット取得を中止したり、ボタンを無効化したりしないこと。
`permissions.contains` のパターン判定は取り違えが起きやすく、**正常な環境を弾いた実績がある**
（`/get-chat-feature-spec` 6節）。**注入の成否だけが権威**であり、事前判定は
「失敗したときの文面を良くするため」にしか使わない。

⚠️ **判定できないことを異常として出さない。** `hasYouTubePermission()` は判定不能のとき
`true` を返し、A側も `ytPermission === null`（未応答）は緑のままにする。
**`=== false` のときだけ橙**にする。

⚠️ バッジの優先順位は **版数不一致・アドオン未検出 > 権限なし**。
「権限なし（橙）」と「アドオン未検出（赤）」が区別できないと、この改修の意味がなくなる。

## 6. ➕送信ボタンの仕様（v2.3.0 / v2.3.1 / v2.4.0）

### 6-1. 責務分担

| 項目 | 担当 | 理由 |
| :--- | :--- | :--- |
| 重複判定 | **A側** | B側は枠の現在の状態を知らない。🧹でクリアした枠へ再送信できる必要がある |
| 結果表示 | B側 | 判定結果を受け取って表示するだけ |
| 連打抑止 | 両側 | B側=busyフラグで往復を減らす / A側=最終判定 |

### 6-2. 重複判定キー

URL文字列ではなく **videoId（11文字）** で比較する。プレイリストURLは `'list:<playlistId>'`。
同一動画でも `?t=120s` `?pp=xxxx` `youtu.be/` 等でURL文字列が揺れるため。

A側は `cardVideoKeys{cardId → key}` で枠ごとのキーを保持し、
`getSlotVideoKeys()` が YT Player の `getVideoData().video_id` も併用して照合する
（プレイリスト枠は「リスト自体」と「再生中の動画」の両方が一致対象）。

キーの破棄タイミング: `resetPlayer`(🧹) / `destroyPlayerCard`(🗑) / `handleLocalSelect`（ローカル動画へ差し替え）。

**比較対象の範囲**: 送信ボタン押下時に**全枠の現在の内容**と比較する。
手動入力で入れた動画とも突き合わせるが、**手動入力そのものは一切制限しない**。
弾かれるのは送信ボタン経由の投入のみ（`requestId` が付いている呼び出しのみ判定を行う）。

### 6-3. 🔴 DOMセレクタの大原則

1. **クラス名に依存しない。** YouTubeは `yt-content-metadata-view-model-wiz` →
   `yt-content-metadata-view-model` のようにクラス名の `-wiz` サフィックスを予告なく廃止する。
   完全一致で書くと全滅する。
   → **カスタム要素名（タグ名）を主軸**にし、クラス名を使う場合は `[class*="..."]` の部分一致にする。
2. **IDセレクタは使わず `[id="..."]` の属性セレクタを使う。**
   YouTubeは全カードが同じidを持つ（`#metadata-line` `#video-title` が数十個重複）。
   `element.querySelector('#metadata-line')` は document 全体の最初の一致を評価し、
   「配下に無い」＝null と誤判定されうる。
3. **`findInsertTarget()` は null を返さない。** 最終手段としてカード自体を返す。
   位置は崩れてもボタンが「まったく出ない」より良い。

### 6-4. 挿入仕様

- 対象セレクタ: `ytd-rich-item-renderer` / `ytd-video-renderer` / `ytd-grid-video-renderer` /
  `ytd-compact-video-renderer` / **`yt-lockup-view-model`**（2025年以降の新レイアウト）
- **入れ子対策**: ホーム画面は `ytd-rich-item-renderer` の内側に `yt-lockup-view-model` が入り
  両方がセレクタに一致する。`card.querySelector(cardSelectors)` で子孫に一致要素があれば
  外側をスキップし、**内側を優先**する
- 挿入先の優先順位: `[id="metadata-line"]` → `yt-content-metadata-view-model` →
  `[class*="content-metadata-view-model"]` → `yt-lockup-metadata-view-model` →
  `[id="meta"|"details"|"byline-container"]` → タイトルの親 → カード自体
- サムネイル上へのオーバーレイは、ホバー時の自動プレビューがサムネイル領域をDOMごと
  差し替えるため**不採用**
- タイトル取得: 専用タイトル要素 → `title`属性 → `aria-label`
  （`by` / `投稿者:` / `作成者:` で分割＝多言語対応）
- Shorts除外: href の `/shorts/`、`ytd-reel-*` / `ytm-shorts-lockup-view-model` の祖先・子孫、
  `[overlay-style="SHORTS"]`
  ⚠️ **`ytd-rich-shelf-renderer` を無条件に除外してはいけない。** Shorts以外のシェルフでも
  使われ通常動画を巻き添えにする。必ず `ytd-rich-shelf-renderer[is-shorts]` と属性で限定する

### 6-5. ボタンUI（v2.4.0で分割型に変更）

```
┌──────────┬────┐
│  ➕ 送信  │ ⧉ │   ← 1つのボタンを左右2分割したセグメント型
└──────────┴────┘
```

- 外側の `<span class="sync-btn-group">` が角丸・影・`overflow:hidden` を持ち、
  内側の2つの `<button>` は `border-radius:0` にして境界線だけで区切る
- 左（`sync-send-to-controller-btn`）: コントローラーへ送信。結果で色が変わるのは**左だけ**
- 右（`sync-copy-url-btn`）: URLをクリップボードへコピー。`✓`(緑) / `✗`(赤) を1500ms表示
- `type="button"` を明示し、`preventDefault` / `stopPropagation` /
  `stopImmediatePropagation` の3点セットでYouTube側のカード遷移ハンドラを止める

### 6-6. URLの整形（buildCleanUrl）

hrefには `pp=`（トラッキング）や `si=` が付く。同時視聴で意味を持つ
**`v` / `list` / `t` / `index`** だけを残して再構築し、送信・コピーの両方で使う。

### 6-7. クリップボード実装

`navigator.clipboard.writeText()` を第一手段とし、
**失敗時は画面外テキストエリア + `execCommand('copy')`** へフォールバックする。
フォールバック用テキストエリアは `display:none` にしてはいけない（選択できずコピーに失敗する）。
`position:fixed` で画面外へ逃がすこと。manifest の `permissions` に **`clipboardWrite`** が必要。

### 6-8. カード再利用対策・監視方式

YouTubeはスクロール時にカードのDOMを**使い回す**（要素はそのままで中身だけ差し替わる）。
- クリックの瞬間にカードからURL/タイトルを再取得する（`resolveCurrent()`）
- 挿入済み判定は **フラグ + 実物（`.sync-btn-group`）の存在** の両方を確認する

監視は `MutationObserver` + `yt-navigate-finish` イベント + `setInterval` 2秒（自己修復）の3系統。
実行は `scheduleScan()` で300msデバウンスして束ねる。

`DEBUG = true` のとき、挿入0件なら内訳（`nested` / `already` / `noLink` / `shorts`）を
`console.warn` へ出力する。

## 7. チャット機能のプロトコル

**→ 実装の詳細は `/get-chat-feature-spec` を参照。**

### 7-1. A側は分割を意識する必要がある

| メッセージ | 内容 | タイミング |
| :--- | :--- | :--- |
| `chatMeta` | `videoMs`, `ok`, `error` | watch HTML 解析直後（実測 約1.0秒） |
| `chatChunk` | `seq`, `comments[]`, `emoji{}` | 取得しながら逐次（初回 実測 1.2〜1.7秒） |
| `chatDone` | `total`, `complete`, `elapsed` | 完了時 |

- `emoji` は**そのチャンクで新規に見つかったぶんだけ**を載せる（辞書全体を毎回送らない）
- `comments` は `t` 昇順。**チャンク間の順序も保持される**（実測）
- `seq` は通し番号。A側で欠番検出に使う（欠番を検出したら `store.gap` を立て、
  **キャッシュに保存しない**）
- `complete` は動画長（`lengthSeconds`）と最終コメント位置の照合結果

### 7-2. 束ね規則（段階1-F で確定）

```
先頭 3 リクエスト     … 即送信（初回到達 1.2〜1.7秒）
以降 20 リクエストごと … 束ねて送信（1メッセージ 約900件・約60KB）
```

20で「取得だけの床」に到達する。50以上にしても速くならず間隔が伸びるだけで、
**100は巨大メッセージの構造化複製が効き始めて逆に遅くなる。**

### 7-3. 🔴 最終チャンクは `chatDone` に同梱する

別メッセージにすると、A側が `chatDone` を受けて片付けたあとに最終チャンクが届き、
**そのぶんが丸ごと消える。** 段階1-F で検証アドオンが7回中7回これを踏んだ。

A側は `chatDone.total`（取得側が数えた件数）と自分の保持件数を**必ず突き合わせる**こと。
静かに減るのが一番まずいので、不一致は画面に出す。

### 7-4. ⚠️ 中間2ファイルでのフィールド欠落に注意

`background.js` と `content_controller.js` の**両方**で全フィールドを明示転送すること。
4節の `relativeSeekReport` の `diff` が中間ファイルで削られている既知バグと同じ構造にはまる。

### 7-5. A側レイアウトの既知の罠

- チャット欄の幅は **px ではなく枠に対する割合(%)** で保持する。
  px固定だと枠が小さいときに flex が縮められず、グリッドのトラック幅を押し広げてしまう
- `.player-container` の `min-height` は **0**。100px を残すと「下配置」時に枠が膨らむ
- 比率の範囲は 15%〜70%（`CHAT_RATIO_MIN` / `CHAT_RATIO_MAX`）

### 7-6. 取得失敗の理由コード ★v2.6.4

**プロトコル上の取り決めはこれだけ**: `chatMeta` / `chatDone` の **`error` 文字列の先頭に
理由コードを載せる。** メッセージもフィールドも増やさない。
書式は `CODE: 日本語の説明`（半角コロン＋スペース区切り）。

| 理由コード | 意味 |
| :--- | :--- |
| `MEMBERS_ONLY` | 再生自体ができない（メンバー限定・年齢制限など） |
| `NOT_LIVE_ARCHIVE` | ライブ配信のアーカイブではない（通常動画） |
| `CHAT_DISABLED` | チャットのリプレイが無効 |
| （コード無し） | 権限・通信・注入など原因未確定 |

A側は `/^([A-Z_]+):\s*([\s\S]*)$/` で分解する。

🔴 **理由コードを画面に露出させないこと。** A側で必ず分解してから表示する。

- B側の判定ロジック（`findPlayerResponse` / 判定順の根拠）→ `/get-chat-feature-spec` 1-5節
- A側の文言と出し分け表（見出しの全文・切り分け手順の全文）→ `/get-chat-feature-spec` 8-8節

⚠️ **理由コードを増やすときもプロトコルは変わらない**（文字列の中身が増えるだけ）。
ただし**A側が知らないコードを受け取ると「コード無し」扱いにならず、見出しが空になる**ため、
B側でコードを足したら必ずA側の分岐も同時に足すこと。

### 7-7. 「取得成功かつ0件」はプロトコル上の成功である ★v2.6.5

`chatMeta` が `ok:true`、`chatDone` が `ok:true` で `total:0` という組み合わせは**正常な成功**である。
`error` も理由コードも付かない。**B側は「取れなかった」ではなく「0件だった」としか言えない**ため、
これを異常として扱う判定は**A側に置く**。

| 側 | 責務 |
| :--- | :--- |
| B | 取得できたものを送る。0件でも `ok:true` で `done` を返す |
| **A** | `store.comments.length === 0` を見て専用表示へ分岐する |

⛔ **理由コード `EMPTY_REPLAY` は作らない。** B側から見て「空で返った」と
「本当に0件だった」は区別できないため、コードを足しても意味が増えない。
**メッセージもフィールドも増やさない**（＝この機能でプロトコルは変わっていない）。

A側の表示仕様は `/get-chat-feature-spec` 8-9節。

## 8. 既知の不具合・恒久的な制約

⚪ **【v2.7.1 で解消】読み込んだ動画URLが再読み込みで消える**

原因は `resaveUrlsBasedOnOrder()` が **DOM（`urlInput_*`）を情報源にしていた**こと。
症状・原因・`sync_url` を触る10経路は `history_protocol.md`。

| 残す前提 | 内容 |
| :--- | :--- |
| 情報源 | **`cardUrls`（cardId → URL）をメモリに持つ。DOM は見ない。** 入力欄が生きている枠は入力欄を優先 |
| 明示的な全消し | **`clearAllSettings()` のみ** |
| 🔴 保存キー | **`sync_url_<cardId>` と `sync_url_<枠番号>` の2系統のまま。統一していない。** 触る改修では両方の寿命を揃えること |
| ⚠️ | **`resaveUrlsBasedOnOrder()` の呼び出しを減らさないこと**（並び替えと枠削除で番号キーを詰め直すため） |

⚪ **【仕様】枠数を減らして戻すと、前の動画が復活する**（2026-08-02 / 利用者判断で容認）

`changePlayerCount()` で枠を減らすと `compactSavedUrls()` が番号キーを詰め直すが、
その後 `resaveUrlsBasedOnOrder()` が走らないため、減らしたぶんの番号キーが `localStorage` に残る。
枠数を戻すとその枠に前の動画が復活する。

**不具合ではなく仕様として容認する。** 枠数の増減は「表示する枠の数」の操作であって
動画を捨てる意思表示ではない（捨てる入口は🧹と🗑と「全設定・保存URLをリセット」）。
利用者要望「押さない限り保持してほしい」にも沿う。

⚠️ **`compactSavedUrls()` は番号を詰め直すため、戻る枠が減らす前と同じとは限らない。**
これも容認済み（2026-08-02）。**版数を切らない。**

🔴 **【最重要】MV3のバックグラウンドは30秒アイドルで終了する**

MV3 の `background.scripts` は**イベントページ**であり、無活動が続くと終了する。

**症状**: `Error: Could not establish connection. Receiving end does not exist.`
起動直後は動くのに、**しばらく操作していると急に通信できなくなる**ため原因を誤認しやすい。

**設計上の帰結**
- **数十秒〜数分かかる処理をバックグラウンドに置いてはいけない。**
  9本のチャット取得は並列3で約3.5分かかるため、これを直撃する
- 取得ループは**注入先のタブ側**（MAIN world）に置く。タブはアイドル終了しない
- **バックグラウンドは中継に徹する。** メッセージが流れ続ける限り生存が維持される
  （実測で4,252回の中継を脱落なく完走）
- 拡張機能ページ（`browser.runtime.getURL()` で開いたタブ）は `browser.scripting` /
  `browser.tabs` / `browser.permissions` を直接呼べる。**バックグラウンドを経由する必要はない**
- ⚠️ **短時間で返る処理は問題を隠す。** v2.5.x の C側経路が無事だったのは数秒で返っていたため

🔴 **【最重要】`playing` イベントでシーク完了を判定してはいけない**

`currentTime` への代入によるシークは**非同期**に進む。代入直後に `play()` を呼ぶと、
**まだ落ちていない古い `readyState`** を見て `playing` が即座に発火し、
シーク未完了のまま「完了」と誤判定する。

**症状**: 計測すると常に 0〜1ms。一見「速くて良好」に見えるため気づきにくい。
**正しい判定**: `seeked` イベント **かつ** `readyState >= 3` の両方。
差分が微小でシークが発生しない場合は `seeked` が飛ばないため、ポーリング併用で取りこぼしを防ぐ。

🔴 **プロセス間メッセージは fetch より重い**

`runtime.sendMessage` はプロセスをまたぐため構造化複製が走る。
**1メッセージあたり約120ms**（ペイロード約3KB）。fetch 自体が約100msなので**中継の方が重い。**
束ねなしで送ると全体が **×2.14** に膨れる（7-2節の束ねで実質消える）。

**細かいメッセージを大量に送る設計は避けること。**

⚠️ **並列3で測ると回線が律速（約22 req/秒）して中継コストが隠れる。**
この種の計測は必ず**逐次**で行う。

🟡 **バックグラウンドタブの `setTimeout` はクランプされる**

Firefox は `dom.min_background_timeout_value`（既定1000ms）で背面タブのタイマー下限を丸める。

→ 「絶対時刻を送って各所が `setTimeout` で自走する」方式は**採用不可**。
発火はフォアグラウンド確定のA側（コントローラータブ）で完結させること。
`performance.now()` ポーリングに置き換えても同じクランプを受けるため回避できない。

**ただしメッセージ配送も fetch も間引かれない。** `runtime.sendMessage` / `tabs.sendMessage` は
イベント駆動でタイマー抑制の対象外（実測で背面タブの往復 0〜7ms と前面より速い）。
fetch も同様で、背面タブで16分間走らせても最大チャンク間隔は1,055msにとどまった。
**取得ループに `setTimeout` を混ぜない限り間引かれない。**

🟡 **対応配信サイトは実質2つのみ**

`manifest.json` の注入対象が dアニメストア と Amazon のみ。Netflix等はデッドコード。
拡張する場合は `host_permissions` と `content_scripts.matches` の**両方**に追記が必要。

🟡 **manifestはFirefox専用**

`background.scripts` 形式のためFirefox専用（Chromeは `service_worker` が必要）。
**`world:'MAIN'` は Firefox 128以降**（実測環境は 153。manifest の `strict_min_version` は 140）。

⚪ **修正済みの不具合は `history_protocol.md` を見ること**（v2.3.0 の3件）。

## 9. テスト・検証の進め方

### 9-1. 本番環境に組み込む前に単体で検証する

いきなりコードへ統合せず、**切り分け可能な最小単位でテストする。**
2026-07-26 の取得方式検証は、**別IDの独立したテストアドオン**で全段階を通した。
本番コードに一切触れずに確認でき、現行リリースを壊すリスクがない。

段階の切り方の原則: **アドオン不要な範囲 → タブ1枚 → 注入 → 複数本 → 中継 → 定数の掃引**。
外側から1つずつ条件を足していくと、どこで壊れたかが必ず1手で分かる。

### 9-2. テスト手順書の作り方

**→ `/get-dev-workflow` 2節を参照。** 依頼のたびに新しく作ること、項目ごとに自己完結させること、
画面に出る文字列を略号でなく全文で載せることが規約になっている。

### 9-3. 計測スクリプトの「1周目」を信用しない

ループの1周目だけが極端に速い値を返す現象に、検証中**3回かかった**。
原因は1周目だけ前提条件が揃っていないこと。

- ループの前に**捨て打ち（ウォームアップ）を1回入れる**か、1周目を集計から除外する
- 集計の「幅（最大−最小）」が異常に大きいときは、**ばらつきではなく条件混在を疑う**
- 性質の違う測定を1つの集計に混ぜない

### 9-4. 「決定的なテスト」を宣言するときは慎重に

過去、iframe方式の検証で「これが決定的」と3回宣言し3回とも外した。
前提条件（実行コンテキスト、オリジン、リクエスト形式）が揃っているかを先に確認すること。

**同じ理由で、v2.6.0 で C側を即撤去しなかった。** 全段階の検証を通過しても、
実運用は検証環境より過酷なのが常なので退路を残した。撤去は v2.6.2。

### 9-5. 実測は設計案をよく否定する

**5つの版で、事前想定が合計16項目ひっくり返っている**（v2.4.3 で4件 / 取得方式検証で6件 /
段階1-F で3件 / 段階3-A で1件 / v2.7.0 で2件）。**性能・比率に関する直感は当てにならない。**

代表例:

| 事前の想定 | 実測 |

## 10. 再生同期の実測仕様 ★v2.4.3

**プロトコルへの追加メッセージはない。** 改修は `controller.html` のみで完結する。

### 10-1. 実測値（2026-07-25 / Firefox / GitHub Pages / 1枠での単独測定）

| 経路 | 一括停止→再生 | シーク後の再生開始 | 初回再生（COLD） |
| :--- | ---: | ---: | ---: |
| ローカル動画 | 0〜2ms | **シーク自体に最大2000ms** | — |
| YouTube | 10〜12ms | **295ms**（幅4ms・固定） | 432〜618ms（幅186ms） |
| 外部動画（dアニメ） | 0〜1ms | 約1ms | — |

A→B→A の往復遅延: 前面タブ 3〜18ms / 背面タブ 0〜7ms。

### 10-2. 結論：問題は「再生」ではなく「シーク」だった

一括停止→一括再生の3経路の最大差は **12ms**（60fpsで1フレーム未満）。**対策不要。**
真因は `applySeekToAll()` が3経路へシークを投げっぱなしにして即座に戻っていたこと。

### 10-3. ローカル動画が遅い理由 ─ キーフレーム間隔

検証素材（106分）のキーフレーム間隔が **30秒**。30の倍数以外へ飛ぶと直前のキーフレームからの
デコードが必要になる。

| 目標位置 | 45s | 60s | 75s | 90s | 105s |
| :--- | ---: | ---: | ---: | ---: | ---: |
| シーク所要 | 752ms | 70ms | 1129ms | 58ms | 962ms |

75s の反復は 872 / 846 / 848ms で再現性あり。`buf待ち 0ms` / `readyState 4` であることから、
**I/Oでも先読み不足でもなくデコード時間**。根治には再エンコードが必要。

```
ffmpeg -i 入力.mp4 -c:v libx264 -preset fast -crf 20 -g 60 -keyint_min 60 -sc_threshold 0 -c:a copy 出力.mp4
```

`-g 60` は30fps時の2秒相当。**`-c:v copy` では変わらない**（映像の再エンコードが必須）。

### 10-4. 採用した設計（`applySeekToAll()`）

```
① 再生中なら全経路を停止（isPlayingRequest は落とさない＝ボタンは「一括停止」のまま）
② ローカル動画の待機を「シーク発行より先に」仕掛ける（後から登録すると seeked を取り逃す）
③ 3経路へシークを発行
④ 全ローカル動画の 'seeked' + readyState>=3 を待つ（上限3000ms）
⑤ 揃ったら経路別オフセットで再開
     t=0ms   … YouTube へ playVideo()
     t=290ms … 外部動画へ play を送信
     t=295ms … ローカル動画へ play()
```

**設計原則: 観測できないものを無理に待たず、観測できるものだけ待つ。**

| 仕掛け | 目的 |
| :--- | :--- |
| 上限3000msで強行再開 | 待ち続ける実装は、シーク失敗時に**永久に再生が始まらない**（沈黙不具合） |
| `seekSettleToken`（世代番号） | 待機中の再スキップで古い `Promise.all` が後から発火するのを防ぐ |
| `countdownOverlay` に「準備中…」 | 待機を停止と誤認させない |
| 停止中のシークは待たない | 次の一括再生で揃うため不要 |

⚠️ 完了判定に `playing` イベントを使ってはいけない（8節🔴）。

### 10-5. 定数

| 定数 | 値 | 根拠 |
| :--- | ---: | :--- |
| `YT_PLAY_LEAD_MS` | 295 | 実測 297/298/298/301ms（幅4ms） |
| `EXT_PLAY_LEAD_MS` | 5 | A→B 片道の実測 |
| `SEEK_SETTLE_TIMEOUT_MS` | 3000 | 安全弁 |

**環境（回線・PC）が変われば再測定して更新すること。**

### 10-6. ⛔ 撤回した設計 ─ 旧「プリバッファ方式（v2.5.0案）」

`prime` / `readyReport` / `play.startAt` 方式は、実測により**不要かつ一部は有害**と判明した
ため撤回した。**再提案しないこと。**

| 旧案 | 撤回理由（実測） |
| :--- | :--- |
| `getVideoLoadedFraction()` の閾値でYouTubeの読込率を判定 | **長尺動画では常に微小。** 106分の動画で 0.007→0.008 しか動かず閾値判定が原理的に成立しない |
| `play` に `startAt`（絶対時刻）を載せ各所が `setTimeout` で自走 | 背面タブのタイマークランプで**現状より悪化する**（8節🟡） |
| `startAt` の待機を `performance.now()` ポーリングで補正 | ポーリング自体が同じクランプを受けるため無効 |
| 配信サイトへ `prime`（ミュート先読み）を送る | 外部動画は 0〜1ms。**先読みの必要がない** |
| 目標を「誤差±200ms前後」とする | 保守的すぎた。実測で再生12ms・シーク後4ms幅を達成 |

### 10-7. YouTube の性質（再確認）

- **停止中はバッファリングしない。** シーク後に1.5秒待っても再生開始は295msから縮まらない。
  → 「待って温める」方式は無効。**定数先行が唯一の手段。**
- 読み込み完了の判定は `getVideoLoadedFraction()` ではなく
  **`onStateChange` の `PLAYING(1)` 到達**。
- `loadSingleYT()` には `onStateChange` ハンドラが**未登録**。COLD対策を実装する際は追加が必要。

### 10-8. COLD再生の残課題（→ v2.9.0 で対応）

初回再生（COLD）の 432〜618ms・幅186ms は未対応。9枠同時では帯域競合でさらに広がる。

対処案: プリロール方式（無音で一瞬走らせ `PLAYING(1)` 到達を確認 → `seekTo` で頭出しを戻す）
＋点呼で全枠を揃える。**`tabKey` 付きの点呼メッセージ追加が必要＝プロトコル変更。**

⚠️ 点呼を実装する際は、`background.js` と `content_controller.js` の**両方**に
新フィールドの転送を明示追加すること（7-4節）。

**v2.9.0（リアルタイム同時視聴）に統合する。** ライブは巻き戻しもシークもできないため、
ズレを直す手段が初回再生の同期しかなく、点呼方式がそのままライブ用の頭出し合わせに使えるため。
