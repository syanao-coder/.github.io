# スパイク S1 指示書 ─ コメント流しのカクつきの切り分け

発行: 2026-10-11（Claude Code）
基点: `index.html` v2.11.1（**本番コードへの変更なし**）
読む仕様書: `get-dev-workflow`（1-4節・3-1-2節「スパイクに限り計測スニペット」）/ `get-debug-suite`（9-C節）/ `get-danmaku-spec`（1節）

## 1. きっかけ（利用者 2026-10-11）

- 動画が2〜3本でもコメント流しがカクつくことが多い。**アーカイブとライブの両方で起きる。**
- **カクつくのはコメントだけ**（枠を増やしすぎて PC の性能を使い切ると動画も含めて全体がカクつく）。
- 利用者の案: コメントを1件ずつ独立して流すのではなく、**透明な四角が群れで流れるアニメーションを先に用意し、そこにコメントを載せる。** 密度とタイミングは、コメントの量ではなく四角の数・大きさ・速度で決まる。

## 2. 着手前に実コードで確かめたこと

| # | 確認 | 結果 |
| :-: | :--- | :--- |
| 1 | 移動 | `flowRafLoop()` が**メインスレッドで毎フレーム**、全コメントの `style.transform` を書く（D3 方式・`get-danmaku-spec` 1-1節） |
| 2 | 時刻源 | アーカイブは 250ms ごとに `getChatPlayheadMs()` で位置を取り直し、フレーム間は補間（`flowEstMs`）。取り直すたびに位置が前後に跳びうる（コードに「一瞬だけ巻き戻ることがある」の注記）。**ライブは `performance.now()` の実時計**で、この揺れは無い |
| 3 | 生成 | 250ms の tick でまとめて生成（`pumpFlowProgress` → `flowSpawn`）。要素を作り、canvas で幅を測り、`appendChatBody` で本文を組む |
| 4 | 見た目 | `.flow-msg` は `will-change: transform` と**ぼかし付きの影4重**（`text-shadow: 1px 1px 2px #000, …`） |
| 5 | 過去の結論 | `get-danmaku-spec` 1-2節①「CSS に任せれば軽い、は誤り（9枠で rAF 方式の fps 最低が 36%高い）」。🔴 **ただしこの fps はページ側（メインスレッド）の rAF で測った値**で、合成器側の滑らかさは測っていない可能性がある（仮説） |

## 3. 仮説

**「動画は滑らかでコメントだけカクつく」「ライブでも起きる」** から、時刻源の揺れ（#2）だけでは説明できない。
Firefox では動画の描画と CSS / Web Animations の `transform` アニメーションは**合成器（メインスレッドの外）**で進む。
コメントはメインスレッドで位置を書いているので、**ページ側が一瞬詰まるとコメントだけが止まる。**

| 候補 | 見分け方（S1 のモード） |
| :--- | :--- |
| A. メインスレッドの詰まりで位置の書き込みが遅れる | **F3/F4（合成器で動かす）だけ滑らか** |
| B. 縁取り（ぼかし影4重）の描画が重い | **F2/F4（縁取りなし）で滑らかになる** |
| C. アーカイブの時刻源の揺れ | アーカイブだけ「時刻源の揺れ」の巻き戻り・30ms超が多い。F3/F4 でも直らない場合は別要因 |
| D. 生成の山（tick ごとのまとめ生成） | 「1tickの生成数の最大」「生成の合計時間」が大きく、F3/F4 でも残る |

## 4. 計測コード（`tests/spike_flow_s1.js` / `flow-s1-1.0.0`）

本番の関数を**計測中だけ包み、終わったら戻す**（`flowRafLoop` / `flowSpawn` / `pumpFlowProgress` / `pumpChatProgress`）。

| モード | 中身 |
| :--- | :--- |
| `D-F1` 基準 | 何も変えずに測る |
| `D-F2` 縁取りなし | `<style>.flow-msg { text-shadow: none !important; }</style>` を足す |
| `D-F3` 合成器で動かす | 生成した要素に `el.animate()`（`transform` の Web Animations）を付け、rAF ループは**位置を書かず**、消すのと一時停止の反映だけを行う。🔴 アーカイブでも実時計で進むので、20秒のあいだに少しずれうる（スパイクなので許容） |
| `D-F4` | F3＋縁取りなし |

- 各モード20秒・間に3秒。出力は `debug_suite.js` と同じ書式（用紙の3つの照合がそのまま効く）。
- 測る値: ページ側のフレーム間隔（中央・95%・最大・落ちたフレーム）、流しの1フレームの処理時間、tick の処理時間（チャット欄・流し）、1tick の生成数と生成の合計時間、同時表示、アーカイブの時刻源の揺れ（描いた位置の進み − 実時間 × 速度。巻き戻り・30ms超の回数）。
- 判定（切替が効いたか）: F2/F4 は計測中のコメントの `text-shadow` が `none`、F3/F4 はアニメーションを1個以上作れた。PC: 流しの枠が1つ以上・平均1件以上流れている・300フレーム以上数えた。
- 🔴 **合成器側の滑らかさは JS からは測れない。** F3/F4 の見た目は利用者の目視（用紙の R1a〜d・R2a〜d）が主たる判定。

## 6. 結果の読み方（次の一手）

| 結果 | 次の一手 |
| :--- | :--- |
| **F3/F4 だけ滑らか** | 動きを合成器へ移すのが本筋。利用者の「四角の群れ」案（要素を使い回し、常に流れ続ける四角に載せる）と、もっと小さい「コメントごとに `el.animate()`」案を S2 の試作で比べる（3枠・9枠） |
| F2 で滑らか | 縁取りを軽い方式へ（ぼかしなしの影・`-webkit-text-stroke` など）。パッチで済む |
| アーカイブだけ揺れが大きく、F3/F4 でも残る | 時刻源を滑らかにする（取り直しで位置を跳ばさず、少しずつ寄せる） |
| どれも滑らかにならず、フレーム落ちが多い | ページ全体の詰まり。tick の処理時間の内訳を次のスパイクで追う |

## 8. 追記（2026-10-22）: 計測コード 1.1.0

v2.12.1 の測定で「4枠で**音量メーターのバーとコメントが同時に**カクつき、**動画は滑らか**」と分かった（`report_v2_12_1.md`）。バーは v2.12.1 から rAF で毎フレーム描いているので、**ツールのページのメインスレッドの詰まり**（仮説 A）がいっそう有力になった。

- `flow-s1-1.1.0`: `renderMeters` と `handleEmbedMessage` も包んで時間を測る。**落ちたフレームで失った時間（ms/秒）**と**自前の処理の合計（ms/秒）**を並べる（失った時間の方がずっと大きければ、詰まらせているのは自前の処理ではない）。ページへ届くメッセージの量（件/秒・YouTube から・文字数）も数える。
- 用紙: 4枠・🔊 パネルを開いたまま測る。`about:processes` で YouTube の枠が別プロセスか（Fission）を確かめる（同じプロセスなら YouTube の処理が同じスレッドを使う）。
- headless（Chromium・偽のライブ1枠・パネルを開いたまま）: 4モードとも PC 成立。失った時間 2〜12 ms/秒・自前 23 ms/秒（流し 8.6 / tick 9.5 / メーター 5.2）。
